```
      │
      ↓
 LOAD BALANCER

      │
```

# 1. The Interview Game 🎯

## 1.1 Why System Design Matters ⭐⭐⭐ `[0:00]`

```
 Most SWE jobs expect it
        │
        ├─ senior / staff  → deciding factor
        └─ mid-level       → now expected too
                              (AI writes the code,
                               so companies want people who
                               understand the BIG PICTURE)
```

Companies want to know if you can:

```
✔ see the big picture
✔ know how components talk to each other
✔ design a solution from scratch
✔ discuss trade-offs
```

## 1.2 Four Interview Formats `[2:19]`

```
 ┌─────────────────────────────────────────────┐
 │ 1. WHITEBOARD   design a system from scratch│  ← most common
 │ 2. BOTTLENECKS  "here's our infra, fix it"  │
 │ 3. PAST PROJECT "explain what you built"    │
 │ 4. CONCEPTS     "what is sharding?"         │
 └─────────────────────────────────────────────┘
```

Even if you know every concept, you still need a **framework** to survive 45-60 minutes.

## 1.3 Why It Feels Hard `[3:17]`

```
  CODING ROUND                 SYSTEM DESIGN ROUND
  ─────────────                ───────────────────
  clear input / output         vague requirements
  you can run tests            nothing to "run"
  one right answer             no single right answer
  "does it work?"              "how do you THINK?"
```

> In system design **YOU** must clarify the vague problem, lock the scope, and define the output.

## 1.4 The 5 Things You Are Scored On ⭐⭐⭐ `[4:51]`

Most people only memorize architectures (1 out of 5!).

```
        ┌─────────────────────────────────────────┐
        │             YOUR SCORE                  │
        └─────────────────────────────────────────┘
          │        │         │         │        │
          ↓        ↓         ↓         ↓        ↓
     COMMUNI-  STRUCTURED TECHNICAL PRACTICAL  TIME
     CATION    THINKING   JUDGMENT  DEPTH     MANAGEMENT
```

| # | Pillar | Interviewer asks | You show it by |
|---|---|---|---|
| 1 | **Communication** | Do they ask questions or just assume? Easy to work with? | Clarify first, think out loud |
| 2 | **Structured thinking** | Clear steps, or random jumping? | Say your outline, know "now / next" |
| 3 | **Technical judgment** | WHY SQL? WHY this cache? | Justify with requirements, mention alternatives |
| 4 | **Practical depth** | Do they think about failures and scale? (shipped real systems?) | Talk about what can break |
| 5 | **Time management** | Stuck on one area? Only high-level done? | Ask where to focus, watch the clock |

💡 Each pillar = how you'd behave at **real work**. Bad time management here = bad time management on the job.

🎤 **Tip:** Ask the interviewer early *"Where would you like me to focus?"* and always know how much time is left.

## 1.5 Time Split for a 60-Minute Interview `[9:44]`

```
 Step 1  Requirements        ████████         5-10 min
 Step 2  Data model + API    ███████████████  15-20 min
 Step 3  High-level design   ███████████████  ~15 min
 Step 4  Scale + reliability █████            5-10 min
 Step 5  Trade-offs + wrap   ███              last few min
```

> 60 min is more common than 45. Don't spend more than 15-20 min on any one step.

# 2. The 5-Step Framework ⭐⭐⭐

> **One repeatable structure for ANY system design question.** `[9:21]`

```
 ┌──────────────────────────────┐
 │ 1. CLARIFY REQUIREMENTS      │   5-10 min
 └──────────────┬───────────────┘
                ↓   "Does this scope make sense?"
 ┌──────────────────────────────┐
 │ 2. DATA MODEL + API          │   15-20 min
 └──────────────┬───────────────┘   (can swap 2 and 3)
                ↓
 ┌──────────────────────────────┐
 │ 3. HIGH-LEVEL DESIGN         │   ~15 min
 └──────────────┬───────────────┘
                ↓
 ┌──────────────────────────────┐
 │ 4. BOTTLENECKS / SCALE /     │   5-10 min
 │    RELIABILITY               │
 └──────────────┬───────────────┘
                ↓
 ┌──────────────────────────────┐
 │ 5. TRADE-OFFS + EXTENSIONS   │   last few min
 └──────────────────────────────┘
```

🎤 **Start by saying your outline:**
> "I'll clarify requirements, model the data and APIs, sketch the architecture, then discuss scale, failures, and trade-offs."

---

## 2.1 Step 1 — Clarify Requirements ⭐⭐⭐ `[11:12]`

> ⚠️ **Do NOT design anything yet.** This is the #1 mistake candidates make.

Why? "Design Spotify" takes teams years. You can't build it in 60 min, so **pick the core use cases**.

```
 REQUIREMENTS
     │
     ├── FUNCTIONAL      "what does it DO?"
     │     • main use cases
     │     • who are the users
     │     • what platform
     │     • what is OUT of scope  ← say it explicitly
     │
     └── NON-FUNCTIONAL  "how WELL / how BIG?"
           • daily / monthly active users
           • read : write ratio
           • latency
           • availability (acceptable downtime)
```

**Check-in before moving on** (the interviewer may give a hint):

🎤 *"Does this scope and these requirements make sense before I move to high-level design?"*

```
 They say YES  → you covered everything
 They hint     → you missed something. Fix it now.
```

---

## 2.2 Step 2 — Data Model + API ⭐⭐⭐ `[13:11]`

You can do this **before** or **after** high-level design:

```
 Easier to think in data first?   → do Data/API, then HLD
 Easier to imagine the user flow? → do HLD, then Data/API
 (the speaker usually starts with HLD)
```

**Data model** — decide:

```
 ✔ main entities           (YouTube → videos, users)
 ✔ relationships           (1-to-many, many-to-many)
 ✔ primary keys, foreign keys, indexes
 ✔ how big each record gets
 ✔ what needs STRONG consistency vs EVENTUAL
```

**API** — decide:

```
 ✔ endpoints + request / response format
 ✔ pagination          ✔ error handling
 ✔ rate limiting       ✔ versioning
 ✔ REST best practices
```

**Database choice** — pick one, say **WHY** (given the requirements), and say what you rejected and why.

---

## 2.3 Step 3 — High-Level Design ⭐⭐⭐ `[15:00]`

> Stuck? Start with these **4 blocks** — almost every system has them:

```
 CLIENT → LOAD BALANCER → API SERVERS → DATABASE
                               │
                               └──→ CACHE (optional)
```

Then **walk the user journey** out loud:

```
 Front end (web / mobile / desktop)
      ↓
 API gateway / load balancer
      ↓
 API servers
      ↓
 Cache  (+ optional message queues)
      ↓
 Database
```

```
 ✔ trace a READ request  and a WRITE request
 ✔ if you use a cache → mention TTL + how you invalidate
 ✔ per component, talk Consistency vs Availability (CAP)
```

---

## 2.4 Step 4 — Bottlenecks, Scale, Reliability ⭐⭐⭐ `[16:56]`

> This is where **mid-level** and **senior** candidates separate. Show what breaks under load, not just the happy path.

```
   FIND THE WEAK SPOTS
          │
   ┌──────┼───────────────┬──────────────────┐
   ↓      ↓               ↓                  ↓
  SPOF  FALLBACKS     REDUNDANCY       MONITORING
  single "slower but  multi-AZ         logs, alerts,
  point   works"      replicas,        latency, error
  of fail path        auto-scaling     rate, thresholds
```

💡 Monitoring is often forgotten. Mentioning it screams "senior".

🎤 *"Are there specific failure scenarios you'd like me to cover?"*

---

## 2.5 Step 5 — Trade-offs + Extensions ⭐⭐⭐ `[18:40]`

```
 SUMMARIZE
   ├─ key decisions you made
   ├─ what you PRIORITIZED
   ├─ what you SACRIFICED  (and WHY)
   └─ extensions: "with more time / 10x load I would..."
```

> You can't build a perfect design in 60 min. The goal is to show you **can extend it**.

---

## 2.6 Do and Don't ⭐⭐⭐ `[20:01]`

```
 ✅ DO                                  ❌ DON'T
 ─────────────────────────────          ─────────────────────────────
 ask clarifying questions first         jump into a solution
 treat interviewer as a COLLEAGUE       stay silent and just draw
 suggest 2-3 approaches                 talk non-stop (monologue)
 explain trade-offs for every tool      pick a tool without "why"
 check in after each major step         work like a take-home test
```

⚠️ **Even for obvious choices, explain.** Payments → SQL is obvious, but say *why SQL and why NOT NoSQL*. If you don't, they assume you don't know.

```
   Interview = 2 engineers solving a problem together
   NOT a monologue.   NOT a take-home.
```

## 2.7 ➕ One Sentence for Every Decision

> **"I choose A over B because the requirement is R. The downside is D, and I'd reduce it with M."**

Example:
> "I choose SQL over NoSQL because bookings need strong consistency. The downside is harder write scaling, which I'd handle with read replicas first, then sharding."

# 3. Building Blocks in Plain English ⭐⭐⭐

> ➕ Learn these once. Every case study below is just these blocks combined.

```
 Block             One-line meaning
 ───────────────   ──────────────────────────────────────────
 Load balancer     splits traffic across servers
 Stateless API     any server can serve any user
 Cache             fast memory copy of popular data
 SQL / NoSQL       where the data lives
 Replication       copies of the DB (scale READS)
 Sharding          splitting the DB (scale WRITES)
 Queue / Kafka     a waiting line between services
 Blob storage      cheap storage for big files
 CDN               copies of files near the user
 WebSocket         an always-open two-way connection
 Elasticsearch     a database built only for search
 Idempotency       doing it twice = same result as once
 Rate limiter      stops abuse
```

---

## 3.1 Load Balancer ⭐⭐⭐

💡 A restaurant host who decides which waiter gets the next table.

```
             ┌──────────────────┐ ──→ Server 1
 Users ────→ │  LOAD BALANCER   │ ──→ Server 2
             └──────────────────┘ ──→ Server 3
```

```
 Algorithms :  round robin  |  least connections
 Also does  :  HEALTH CHECKS  (stops sending traffic to dead servers)
 Layer 4    :  routes by IP/port  → used for WebSockets
 Layer 7    :  routes by URL/header
```

## 3.2 Stateless API Servers ⭐⭐⭐

💡 Any waiter can serve any table because the order is on the ticket, not in the waiter's head.

```
 STATEFUL (hard to scale)          STATELESS (easy to scale)
 ────────────────────────          ─────────────────────────
 server remembers you              server remembers nothing
 you MUST hit the same one         any copy can serve anyone
                                   state lives in DB / cache
```

> **To scale a stateless server → just add more copies.**

## 3.3 Cache (Redis) ⭐⭐⭐

💡 A sticky note on your desk instead of walking to the library each time.

```
 request
    ↓
 in cache? ──YES (hit)──→ return instantly ⚡
    │
    NO (miss)
    ↓
 read DB → save in cache (with TTL) → return
```

```
 TTL            = time to live (cache entry expires)
 Invalidation   = delete/update the cache when data changes
 LRU            = when full, evict the Least Recently Used
 Risk           = stale (old) data
```

## 3.4 SQL vs NoSQL ⭐⭐⭐

```
 SQL (Postgres, MySQL)               NoSQL (Cassandra, DynamoDB)
 ───────────────────────             ───────────────────────────
 tables + JOINS                      simple lookups
 ACID transactions                   huge write speed
 strong consistency                  scales out easily
 use for: money, bookings,           use for: messages, events,
          relationships                       logs
```

**ACID** = transactions are all-or-nothing and consistent.

🎤 Always say: *"I chose X because…, and not Y because…"*

## 3.5 Index ⭐⭐

💡 The index at the back of a book — find a topic without reading every page.

```
 No index :  scan ALL rows            (slow)
 Index    :  jump straight to the row (fast)
```

```
 + faster reads        - slower writes, more storage
 Index the columns you search / join on often.
```

> ➕ A plain index helps exact and prefix lookups. It does **not** fix typos. For typo-friendly search use a search engine (Elasticsearch).

## 3.6 Replication (Leader / Follower) ⭐⭐⭐

💡 One master copy of a book, many photocopies for readers.

```
 WRITES ──→ LEADER ──copies──→ FOLLOWER 1 ←── READS
                    └────────→ FOLLOWER 2 ←── READS
```

```
 Scales      : READS
 Problem     : replication lag (follower slightly behind)
 Fix         : after a user's own write, read from the LEADER
               ("read-your-writes")
```

## 3.7 Sharding ⭐⭐⭐

💡 One library split into several buildings by author name.

```
          ┌─ Shard 1 (hotels A-H)
 DB ──────┼─ Shard 2 (hotels I-P)
          └─ Shard 3 (hotels Q-Z)
```

> **Replication scales reads. Sharding scales writes.**

**How to pick which shard?**

```
 MODULO               shard = hash(key) mod N
                      ✔ simple
                      ✘ add 1 shard → almost ALL data moves

 CONSISTENT HASHING   servers + keys sit on a circle
                      key → next server clockwise
                      ✔ add 1 shard → only ~1/N data moves
```

```
                 server A
             .------o------.
          .'                 '.
    key1 *                     o server B
         |         RING        |
    server D o                 * key2
          '.                 .'
             '------o------'
                 server C
```

```
 Few shards, rarely change  →  MODULO
 Adding shards often        →  CONSISTENT HASHING
```

Good shard key = spreads load evenly + keeps related data together (no cross-shard joins).

## 3.8 Consistency (CAP) ⭐⭐⭐

> The video says "CP theorem" — it means **CAP**: when the network splits you must choose **C**onsistency or **A**vailability.

```
 STRONG consistency                 EVENTUAL consistency
 ──────────────────                 ────────────────────
 everyone sees the latest           may be slightly stale
 use: bank balance, booking         use: search results, likes,
      a room                             "online" status
```

💡 Bank balance must be exact. A like-count can be 1 second late.

## 3.9 Message Queue / Kafka ⭐⭐⭐

💡 Order tickets in a kitchen — the waiter drops tickets and moves on; cooks pick them up.

```
 PRODUCER ──→ [ QUEUE ] ──→ CONSUMER(S)
 (fast)                      (work at their own speed)
```

```
 WHY :  ✔ decouple services
        ✔ absorb traffic spikes
        ✔ retry on failure
 DLQ :  Dead Letter Queue = "problem mailbox" for messages
        that keep failing
 KAFKA: topic → partitions → consumer groups
        (partition = unit of parallelism)
```

## 3.10 Blob Storage + Pre-signed (Signed) URL ⭐⭐⭐

Blob storage (S3) = cheap, durable, huge storage for files (audio, images, video).

💡 A signed URL is a **valet ticket / temporary key card** — works for one thing, then expires.

```
 ❌ WRONG   App ──file──→ API server ──→ storage     (server clogged)

 ✅ RIGHT   App ──"I want to upload"──→ API server
            App ←── temporary signed URL ──┘
            App ──file directly──→ BLOB STORAGE
```

> Never move big files through your API/chat servers.

## 3.11 CDN ⭐⭐⭐

💡 A local convenience store stocking popular items so you don't drive to the factory.

```
 User (Europe) ──→ CDN edge (Europe) ──hit──→ file ⚡
                         │ miss
                         ↓
                    Origin storage
```

```
 + low latency   + less load / egress cost on the origin
 - stale content → needs INVALIDATION when files change
 Uses LRU to evict old content
```

## 3.12 Polling vs Long Polling vs WebSocket ⭐⭐⭐

💡 Polling = calling every 2 s asking "anything new?" · Long polling = staying on hold · WebSocket = an open phone line.

```
 POLLING        Client ─"new?"→ Server ─"no"→
                Client ─"new?"→ Server ─"yes!"→     (wasteful, delayed)

 LONG POLLING   Client ─"new?"→ Server ...waits... → msg / timeout
                Client asks again                    (connection churn)

 WEBSOCKET      Client ═══ open once ═══ Server
                either side can push anytime         ✔ real-time
```

```
 WebSocket trade-offs: needs Layer-4 LB, more memory per connection.
```

## 3.13 Elasticsearch + CDC ⭐⭐⭐

Search engine = database built for **search** (not for transactions).

```
 SQL  LIKE '%paris%'  → scans the WHOLE table, no ranking, no typos
 ES                   → inverted index, relevance ranking,
                        typo tolerance, geo ("within 5 km")
```

**Keeping it in sync (CDC = Change Data Capture):**

```
 PostgreSQL (SOURCE OF TRUTH)
      │  write-ahead log
      ↓
 Debezium  (reads the log)
      │
      ↓
 Kafka (one topic per table)
      │
      ↓
 Consumer ──→ Elasticsearch   (eventually consistent)
```

> Transactions are checked in PostgreSQL. Searches use Elasticsearch.

## 3.14 Idempotency ⭐⭐⭐

💡 Pressing the elevator button 5 times still calls ONE elevator.

```
 Client makes a unique ID (UUID) ONCE per action
     ↓
 Server: does this ID already exist?
     ├─ NO  → do the work, save result
     └─ YES → return the saved result (don't redo)
```

Used for: payments, bookings, message sends, retries.

## 3.15 Rate Limiting (Token Bucket) ⭐⭐

💡 A bucket that refills with tokens. Each action costs one token. Empty bucket = blocked.

```
   refill ──→ [ ● ● ● ● ○ ○ ]   capacity 6
                  │
   action costs 1 token
   tokens left?  YES → allow     NO → block (429 / CAPTCHA)
```

Store counters in **Redis** (atomic ops) so all servers share them.

## 3.16 Heartbeat + Service Discovery ⭐⭐

```
 HEARTBEAT   "are you still there?"  ping every 5-10 s
             no reply → connection is dead → clean it up

 SERVICE     servers register themselves; registry health-checks
 DISCOVERY   them (~10 s); the load balancer asks for the
             HEALTHY list and updates its routing table
```

## 3.17 Monolith vs Microservices ⭐⭐

```
 MONOLITH            one app, simple transactions,
                     hard to deploy independently (100s of devs)

 MICROSERVICES       independent scaling/deploy,
 (DB per service)    but distributed-transaction headaches

 PRAGMATIC ✅        separate services in code,
                     SHARE one DB for tightly-coupled data
                     → local ACID transactions
```

## 3.18 Monitoring ⭐⭐

```
 LOGS     what happened            METRICS  numbers over time
 TRACES   path of one request      ALERTS   wake someone up

 Watch: API latency (p95/p99), error rate, saturation
```

## 3.19 Capacity Math Cheat ⭐⭐⭐

```
 1 day = 86,400 s ≈ 10^5 s              peak = 3-5 × average
 1M requests/day ≈ 12 per second
 100M /day ≈ 1,200/s        1B /day ≈ 12,000/s

 KB=10^3  MB=10^6  GB=10^9  TB=10^12  PB=10^15 bytes
```

```
 avg QPS     = (users × actions/day) / 86,400
 storage     = items × size  (× 2-3 for replicas/versions)
 bandwidth   = QPS × payload size
```

🎤 Always end with a **conclusion**: *"So audio dominates → we need CDN"* or *"So it's read-heavy → we need search + cache + replicas."*

## 4.1 Step 1 — Requirements ⭐⭐⭐ `[25:02]`

**Given:** ~**500,000 users**, ~**30 million songs**.

```
 FUNCTIONAL                          NON-FUNCTIONAL / EXTRA
 ──────────────────────────          ────────────────────────────
 ✔ artists UPLOAD songs              ✔ basic monitoring:
 ✔ users SEARCH + PLAY songs           health checks, error tracking,
 ✔ users create/manage PLAYLISTS       performance metrics
 ✔ user PROFILES
```

**Audio facts (assumptions — confirm them!)**

```
 Formats  : OGG, AAC  (compressed, small)
 Bitrates : 64 kbps  → mobile data saver
            128 kbps → standard      (avg file ≈ 3 MB)
            320 kbps → premium
```

---

## 4.2 Step 2 — Capacity Planning ⭐⭐⭐ `[26:33]`

| What | Math | Result |
|---|---|---|
| 🎧 Song storage | 30M × 3 MB | **90 TB** (plan **2-3×** for replicas + re-uploads) |
| 📝 Song metadata | 30M × 100 B | **3 GB** (tiny) |
| 👤 User metadata | 500K × 1 KB | **0.5 GB** (tiny) |
| 🌐 Daily bandwidth | 10-15 songs/user × 3-4 MB per stream | big **egress cost** |

> **Egress cost** = fee cloud providers charge when data **leaves** their network to users.

```
   💡 KEY INSIGHT

   Metadata ▏                  (tiny)
   Audio    ████████████████   (HUGE)

   → AUDIO dominates storage AND bandwidth
   → main storage = OBJECT STORAGE (blob)
```

> ➕ Finishing the bandwidth math: 500K × 10-15 songs × 3-4 MB ≈ **15-30 TB/day**.

## 4.3 Step 3 — High-Level Architecture ⭐⭐⭐ `[29:24]`

```
  Mobile / Web app
        │  HTTP
        ↓
  ┌──────────────────┐   round robin or least connections
  │  LOAD BALANCER   │   + health checks on API servers
  └────────┬─────────┘
           ↓
  ┌──────────────────┐   validates JWT
  │   REST API       │   creates signed URLs
  │   SERVERS        │
  └───┬──────────┬───┘
      │          │
      ↓          ↓
 ┌─────────┐  ┌───────────────┐
 │ SQL DB  │  │ BLOB STORAGE  │
 │metadata,│  │ (S3) audio    │
 │ users   │  │ files         │
 └─────────┘  └───────────────┘
```

| Block | Job |
|---|---|
| Load balancer | spread requests; health checks |
| REST API servers | check JWT, query SQL, make signed URLs |
| SQL database | song metadata + user profiles |
| Blob storage (S3) | the audio files (cheap, durable, huge) |
| **Signed URL** | one-time link that **expires** → audio isn't permanently public |

## 4.4 Flow A — Play a Song (READ) ⭐⭐⭐ `[31:16]`

```
 User taps ▶
    │  GET /songs/{id}
```

## 5.2 Step 2 — Capacity ⭐⭐⭐ `[58:39]`

Think of a **funnel**. Most visitors only browse, but they still create load.

```
 ┌──────────────────────────────────────┐
 │  Visitors viewing hotels      100%   │  → ~1,000 QPS  (reads)
 └───────────────────┬──────────────────┘
                     │ ~10% search
              ┌──────┴───────┐
              │  Searchers   │
              └──────┬───────┘
                     │ ~10% book
                ┌────┴─────┐
                │ Bookings │  → ~17 TPS  (writes)
                └──────────┘
```

Get **one** anchor number from the interviewer, compute the rest:

```
 TOP-DOWN   : 500M visits / month
 BOTTOM-UP  : 1.1B room-nights / year
```

**Writes (bookings per second):**

```
 1.1B room-nights/yr ÷ 2 nights/booking = 550M bookings/yr
 550M ÷ 365                            = ~1.5M bookings/day
 1.5M ÷ 86,400 s                       = ~17 per second  → 17 TPS
```

**Reads (queries per second):**

```
 500M visits/month ÷ 30  = ~17M visits/day
 17M ÷ 86,400            = ~200 visits/s
 × ~5 backend reads/visit (search, availability) = ~1,000 QPS
```

```
   💡 CONCLUSION
   1,000 reads/s  vs  17 writes/s   →   READ-HEAVY system
   Goal: fast reads + CORRECT writes (no double booking)
```

## 5.5 Step 5 — Data Model ⭐⭐⭐ `[1:22:35]`

> 🔑 **You book a ROOM TYPE, not a specific room.** The room number is assigned at check-in.

```
 HOTELS ──< ROOM_TYPES ──< ROOM_TYPE_RATES
   │           │
   │           ├──< ROOMS               (physical room, assigned at check-in)
   │           │
   └───────────┴──< ROOM_TYPE_INVENTORY (per hotel + room type + DATE)

 GUESTS ──< RESERVATIONS ──< TRANSACTIONS
               (room_type, hotel, dates, status)
```

| Table | Key columns |
|---|---|
| `hotels` | id, name, address, location, description |
| `room_types` | id, name, description, capacity, hotel_id |
| `room_type_rates` | room_type_id, package, rate (basic 100, view 150, breakfast 200) |
| `rooms` | id, floor, available, room_type_id, hotel_id |
| `room_type_inventory` | hotel_id, room_type_id, **date**, total_inventory, total_reserved |
| `reservations` | id, room_type_id, hotel_id, guest_id, start_date, end_date, status |
| `guests` | id, first_name, last_name, email |
| `transactions` | id, reservation_id, type (new/change/refund), amount (+/−) |

**Why a separate `transactions` table?** One reservation can have many payments:

```
 reserve  → +200      change dates → +50      cancel → −250 (refund)
```

**The inventory table (the heart of it)**

```
 one row per  HOTEL + ROOM TYPE + DATE  (not per physical room)

 hotel  room_type   date     total_inventory   total_reserved
 ─────  ─────────   ──────   ───────────────   ──────────────
  7      basic      Dec 15        100                92
  7      basic      Dec 16        100                87
  7      basic      Dec 17        100                95
```

```
 ✔ bulk availability updates   ✔ scalable pricing + search
 ✔ simple OVERBOOKING logic
 Pre-fill the next 2 YEARS; a daily cron job adds new dates.
```

**Availability check**

```
 SELECT date, total_inventory, total_reserved
 FROM room_type_inventory
 WHERE hotel_id=? AND room_type_id=? AND date BETWEEN ? AND ?

 allow booking if:
   total_reserved + rooms_to_book  <=  total_inventory × overbooking_factor
```

```
 Example   100 total, 92 reserved, book 1 → 93 <= 100  ✅
 With 10% overbooking: 100 rooms can take up to 110 bookings
```

**Why relational DB?**

```
 ✔ ACID / consistency   → stops double booking
 ✔ read-heavy is fine   → + Elasticsearch for scale
 ✔ clear relationships  → hotels, rooms, reservations, transactions
 ✔ complex joins / aggregates over inventory + pricing + dates
```

## 5.6 Step 6 — Concurrency (Scenario 2: two users) ⭐⭐⭐ `[1:33:08]`

PostgreSQL's default isolation = **read committed**. There's a **gap between checking and writing**.

**❌ The bug**

```
 User A                    DATABASE                    User B
   │── read: 1 left ──────────→│←────── read: 1 left ──│
   │      (check passes)       │       (check passes)  │
   │── write booking ─────────→│                       │
   │                           │←────── write booking ─│
                    💥 DOUBLE BOOKING
```

> Read committed alone is **unsafe** for bookings.

### Fix 1 — Serializable isolation

```
 BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE
```

```
 ✔ simple, fine for LOW TPS
 ✘ transactions block each other at high TPS
 ✘ deadlock risk if rows are locked in different orders
   → use lock timeouts + keep transactions short
```

### Fix 2 — Read committed + row lock (`SELECT ... FOR UPDATE`) ✅ preferred

💡 A bathroom lock: one person at a time **per room**; other rooms are unaffected.

```
 User A                   DATABASE                   User B
   │── SELECT ... FOR UPDATE ──→ 🔒 row locked
   │                            │←── SELECT ... FOR UPDATE
   │                            │     ⏳ B WAITS
   │── check ok, reserved+1 ───→│
   │── COMMIT ─────────────────→ 🔓 unlocked
   │                            │── B now sees updated row
   │                            │── check FAILS → "not available" ✅
```

```
 ✔ same row   → waits its turn
 ✔ other rows → run IN PARALLEL (serializable can't do this)
```

> ➕ Other options: atomic conditional `UPDATE ... WHERE total_reserved < total_inventory`, or optimistic locking (version column + retry). Lock rows in **date order** to avoid deadlocks on multi-night stays.

## 5.7 Sharding ⭐⭐⭐ `[1:34:44]`

> **Shard key = `hotel_id`.** Most queries start with a hotel. All data for one hotel sits on **one shard** → no cross-shard joins, **local transactions**.

```
 shard = hash(hotel_id) mod N      (start with modulo)

 16 shards → 1,000 reads/s ÷ 16 ≈ 62 QPS per shard
             17 writes/s  ÷ 16 ≈ 1 TPS per shard
```

```
 MODULO               add shard #17 → almost ALL data reshuffles
 CONSISTENT HASHING   add shard #17 → only ~1/17 of data moves

 Few stable shards     → modulo
 Adding shards often   → consistent hashing
```

## 5.8 Caching with Redis ⭐⭐⭐ `[1:40:34]`

```
 KEY   = hotel_id + room_type_id + date
 VALUE = total inventory + total reserved
 TTL   ≈ 5 minutes
 (overbooking rate is a fixed config, NOT stored in cache)
```

```
 User searches hotels
        ↓
 in Redis & TTL valid? ──YES──→ show from cache ⚡
        │ NO (miss/expired)
        ↓
 read DB → fill Redis (TTL 5 min) → show
        
 User clicks BOOK
        ↓
 validate against DB (SOURCE OF TRUTH)
        ↓
 update DB → INVALIDATE affected cache keys
```

## 5.9 Search with Elasticsearch ⭐⭐⭐ `[1:40:41]`

**Why not SQL `LIKE`?**

```
 ✘ full table scan (even with indexes)
 ✘ can't rank by relevance
 ✘ can't handle typos ("Pari" ≠ "Paris")
 ✘ bad at geo distance
 ✘ aggregations are expensive
```

**Why Elasticsearch?**

```
 ✔ full-text + relevance ranking
 ✔ fuzzy match (edit distance 1)
 ✔ geo: "hotels within 5 km"
 ✔ fast filters: price 80-180, stars, location
```

**Data is duplicated + flattened (no joins):**

```
 { "hotel_id": 7, "name": "...", "address": "...",
   "location": {...},
   "room_types": [ {...}, {...} ],
   "amenities": [ ... ] }
```

**Keeping it in sync (CDC) `[1:47:46]`**

```
 PostgreSQL = SOURCE OF TRUTH
      ↓ write-ahead log
 Debezium (open-source CDC)
      ↓
 Kafka (one topic per table)
      ↓
 Consumer ──→ Elasticsearch
              (EVENTUALLY consistent)
```

> Transactions → PostgreSQL. Searches → Elasticsearch.

## 5.10 Replication + Global Routing ⭐⭐⭐ `[1:45:19]`

```
  US users     EU users     Asia users
      └────────────┼────────────┘
                   ↓
        GEO / LATENCY LOAD BALANCER
        ┌──────────┼──────────┐
        ↓          ↓          ↓
    US region   EU region   Asia region
    replica     replica     replica
    + Redis     + Redis     + Redis
    + ES        + ES        + ES
        │          │          │
        └──────────┼──────────┘
                   ↓ writes + "recent write" reads
          ONE PRIMARY WRITE DB
          (no cross-region write conflicts)
```

```
 • reads → nearest replica
 • user JUST wrote something? → read from PRIMARY
   (replica may lag = read-your-writes)
 • TPS is low (~17), so ONE primary shard is enough
```

## 5.11 Trade-offs

| Decision | Good | Cost |
|---|---|---|
| Strong consistency for booking, eventual for search | correct where money matters | search may be stale (re-check at booking) |
| Shared DB for coupled services | local ACID | less service independence |
| Row lock vs serializable | parallel for other rows | keep transactions short |
| Modulo vs consistent hashing | simple vs minimal data movement | resharding pain vs complexity |
| Cache TTL ≈ 5 min | fewer DB reads | slight staleness |
| Single primary | no write conflicts | far regions write slower |

## 5.12 Key Takeaways 🧠

```
 • READ-HEAVY: 1,000 QPS vs 17 TPS
 • Strong consistency for booking, eventual for search
 • Book a ROOM TYPE; inventory per hotel + type + DATE
 • Same user twice → client reservation UUID (idempotency)
 • Two users → row lock (FOR UPDATE) or serializable
 • Shard by hotel_id; Redis for hot inventory (TTL 5 min)
 • Elasticsearch for search, fed by CDC from Postgres
 • Replicas per region, ONE primary for writes
```

```
                         ↓                          (offline users)
                  ┌─────────────┐
                  │ MESSAGE     │  Kafka / RabbitMQ
                  │ QUEUE       │
                  └──────┬──────┘
                         ↓
                  MESSAGE STORAGE SERVICE ──→ Cassandra / DynamoDB

   Media:    App ──pre-signed URL──→ BLOB STORAGE (S3) ──→ CDN
   Presence: PRESENCE SERVICE (heartbeats, Redis, publishes online/offline)
```

| Block | Job |
|---|---|
| **Mobile app** | holds the connection, UI, local storage, **retries** |
| **Load balancer** | spreads traffic; must be **Layer 4** for WebSockets |
| **Chat servers** | keep WebSocket open, route messages, track online users |
| **Message queue** | **decouples writing from delivery**; chat server acks "sent" immediately, then queues async |
| **Storage service** | reads queue → writes DB |
| **NoSQL (Cassandra/Dynamo)** | **huge write throughput**, simple queries (user / conversation / time) |
| **Redis cache** | which user is on which chat server — **microseconds** vs DB milliseconds |
| **Blob + CDN** | media files |
| **Notification service** | APNs (Apple) / FCM (Android) push for offline users |
| **Presence service** | heartbeats → online/offline → notify subscribers |

### Polling vs Long Polling vs WebSocket `[2:03:39]`

```
 POLLING       client asks every N s "new msgs?"
               ✘ wastes bandwidth   ✘ delay up to N s
               ✘ millions of useless requests

 LONG POLLING  server holds the request until a msg / timeout
               ✘ constant open/close + HTTP handshakes
               ✘ idle connections eat memory + threads

 WEBSOCKET ✅  one persistent two-way connection
               ✔ real-time push both ways
               ✘ needs Layer-4 LB, more memory per connection
```

```
                                       │
 Load balancer ──"healthy servers?"──→ │
 Load balancer ←── [server 1, server 2] (3 is unhealthy)
        ↓
 updates routing table → traffic only to 1 and 2
```

## 6.8 Multi-Device Sync ⭐⭐⭐ `[2:13:10]`

> Example: A has **3** devices (phone, tablet, desktop). B has **2** (phone, laptop).

```

                          │
              asks REDIS: which devices are online?
                          │
        ┌─────────────────┼──────────────────────┐
        ↓ (sync copy)     ↓ (sync copy)          ↓ (deliver)
  A's tablet          A's desktop            B's phone  (via server B)
  (via server C)      (via server D)         B's laptop (via server E)

                            → B's LAPTOP also marks it read
```

```
              (simple, not perfect)
 NEW DEVICE : incremental sync — only last ~30 DAYS;
              scroll up → fetch older on demand;
              very old → cold storage, loaded lazily
 TRADE-OFF  : ~2× delivery work (each msg goes to many devices)
```

## 6.9 Media — Pre-signed URLs + CDN ⭐⭐⭐ `[2:28:56]`

```
 ❌ WRONG   App → chat server → DB → recipient downloads from chat server
            Chat servers get crushed moving big files!
            (a server with 100K connections can be hurt by ~100 uploaders)
```

```
 ✅ RIGHT

 UPLOAD
 A taps send → asks chat server for a PRE-SIGNED UPLOAD URL
 chat server asks blob storage (S3) → gives URL to A
 A uploads DIRECTLY to S3  → S3 returns media URL
 A sends chat message containing the media URL

 DOWNLOAD
 B gets message + URL
 B taps → asks for PRE-SIGNED DOWNLOAD URL
 B downloads via CDN (best)  or directly from S3 (simplest)
```

```
 Chat servers only carry small messages + URLs.
 URLs expire (TTL).  Media TTL = 30 days = message retention
 → media auto-deletes.

 CDN trade-off: an extra request + more complexity,
                but the speed + cost win is MASSIVE at this scale.
```

## 6.10 Kafka + Batch Writes ⭐⭐⭐ `[2:31:44]`

```
                 ┌──────────── Message storage instances ────────────┐
 Chat servers →  │ KAFKA topic                                       │
                 │  partitions 0-9   → instance 1                    │
                 │  partitions 10-19 → instance 2                    │
                 │  partitions 20-29 → instance 3   (stateless, scale)│
                 └───────────────────────────────────────────────────┘
```

**Inside one instance:**

```
 Kafka consumer  (batch 500, poll every ~100 ms)
      ↓
 Thread pool (20 workers), for each message:
      ├─ validate schema
      ├─ metadata checks (file size limit?)
      └─ enrich: dedup hash, @mentions, link previews, indexes
      ↓
 BATCH WRITER  (collect 1,000 msgs OR every 5 s)
      │   sort + group by conversation
      ↓
 Cassandra  ATOMIC BATCH INSERT
      ↓
 index updater (search + analytics)  →  mark processed
```

**When something fails:**

```
 write fails (e.g., 10 of 1,000 messages)
      ↓
 retry (escalating steps)
      ↓
 still failing → DEAD LETTER QUEUE
      ↓
 eventually: notify user "message not delivered"

 Never delete from the queue until the DB write succeeded.
```

```
 WHY BATCH?
   1 insert    ≈ 5 ms   → 1,000 inserts = 5,000 ms
   1 batch of 1,000 ≈ 50 ms          → ~100× throughput
```

> ➕ In real Cassandra, batches work best when they stay in **one partition** (same conversation). Huge multi-partition batches hurt performance. Grouping by conversation is the right instinct.

## 6.11 End-to-End Encryption ⭐⭐⭐ `[2:39:18]`

> Messages are encrypted on the sender's device and decrypted only on the recipient's. **Even WhatsApp's servers can't read them.** The video uses the **Signal protocol**.

💡 A sealed envelope only the recipient can open. The post office (server) just carries it.

```
 A's device                KEY SERVER                B's device
     │                          │                         │
     │   each device made an identity key pair at         │
     │   registration. PRIVATE key never leaves device.   │
     │                          │                         │
     │── upload PUBLIC key ────→│←─ upload PUBLIC key ────│
     │                          │←─ + ~100 prekeys ───────│
     │                          │                         │
     │── fetch B's identity key + one prekey ──→│         │
     │←──────────────── B's public keys ────────│         │
     │                                                    │
     │  key exchange → both sides get the SAME SESSION KEY
     │                                                    │
     │═══ ciphertext (via chat servers, unreadable) ═════→│
     │                                       decrypts ✔   │
     │
     │  message counter / ratchet → key changes every message
```

> ➕ Precisely: this is **X3DH** key agreement (works even if B is offline) + the **Double Ratchet** (new key per message → forward secrecy). Messages use derived symmetric keys, not "the public key" directly. Groups use **Sender Keys**. Trade-off: the server can't search or moderate content; metadata (who talks to whom, when) is still visible.

## 6.12 Rate Limiting + Abuse Prevention ⭐⭐⭐ `[2:45:00]`

```
 Without limits: scraping, DDoS, spam.
 Limit EACH action type:

   send messages     100 / minute         (token bucket)
   create groups     5+ per hour = suspicious
   upload media      10-100 / minute
   connections       5 different IPs in 1 minute = suspicious
   group invites     counter per user
 (numbers are examples — clarify in requirements)
```

```
 user action
      ↓
 token bucket has tokens?  (Redis, atomic)
      ├─ YES → deduct 1 → allow → write to DB
      └─ NO  → BLOCK: "too many requests, try in 60 s"
                       or require CAPTCHA
```

**Progressive penalties:**

```
 1st abuse  → warning
 2nd        → 1-hour restriction
 3rd        → 24-hour restriction
 then       → account suspended, HUMAN review
 repeated   → permanent deletion
```

```
 Token bucket = capacity + refill rate (differs per action)
 Central store = REDIS with atomic ops
   → users can't bypass limits by "server hopping"
```

## 6.13 Sharding + Replication ⭐⭐⭐ `[2:49:45]`

```
 SHARD BY          GOOD                      BAD
 ───────────────   ───────────────────────   ──────────────────────────
 USER ID           user's messages in ONE    hotspots: heavy users make
                   shard (1 DB to read)      huge shards, light users tiny
 MESSAGE ID        even distribution         reading one user's chat hits
                                             EVERY shard (slow)
 TIMESTAMP         another option            study the trade-offs
```

**A good answer: shard by user ID + duplicate writes + replicas**

```
 A talks to B (A on shard A, B on shard B)

 message ──→ write copy 1 → SHARD A ──replicate──→ REPLICA A ←─ A reads
        └──→ write copy 2 → SHARD B ──replicate──→ REPLICA B ←─ B reads

 ✘ doubles WRITE volume
 ✔ every READ hits only ONE replica = blazing fast
```

```
 SHARDING    → scales WRITES
 REPLICATION → scales READS
 (primary + e.g. 3 replicas, async = eventually consistent;
  reads go to replicas, writes go to the primary)
```

🎤 **Ask the interviewer: "Which matters more, reads or writes?"** Then pick user-ID sharding + replication, message-ID, or timestamp — and state the trade-offs.

## 6.15 When Things Fail 🚨 ⭐⭐⭐

### Redis goes down `[3:00:32]`

```
 WRITE an undelivered message:
      chat server ──→ Redis inbox   (fast)
                  └─→ DB inbox      (durable backup)

 READ pending messages:
      Redis OK?  ──YES──→ read Redis
                 └─NO───→ log it → READ FROM DB (slower, but works)

 Redis recovers → background job re-syncs undelivered rows
                  from DB back into Redis → normal flow resumes
```

### Kafka goes down `[3:06:37]`

```
 one BROKER dies  → replace it, Kafka rebalances partitions

 WHOLE CLUSTER down (rare):
      chat server tries to publish
          │ fails
          ↓
      log error → LOCAL IN-MEMORY BUFFER
                  (max ~100,000; drop OLDEST if full)
          ↓
      wait (longer than time to spin up new Kafka) → retry
          ↓
      chat server ALSO crashes?  → APPEND-ONLY LOG on local disk
          ↓
      on recovery: replay the log, delete it after a successful publish
          ↓
      query processed messages since last ID, republish the missing
      ones, then resume normal consumption
```

```
                                          (LaunchDarkly / cloud native)
              ←── flags per environment + rollout % ──
```

## 6.18 Trade-offs

| Decision | Good | Cost |
|---|---|---|
| WebSocket | real-time, efficient | memory per connection, L4 LB |
| Queue before DB | decoupling, batching, failure handling | extra complexity |
| NoSQL | write throughput | weak joins |
| Redis connection cache | microsecond routing | must handle Redis failure |
| Duplicate writes + replicas | fast reads | 2× writes |
| Multi-device sync | users expect it | ~2× delivery work |
| Pre-signed URL + CDN | light chat servers | extra requests |
| Cleanup jobs | healthy storage | operational overhead |
| Local buffer + disk log | little data loss | bounded memory, replay logic |

## 6.19 Key Takeaways 🧠

```
 • WebSocket for real-time; Layer-4 LB
 • Chat server acks SENT immediately → queue → DB
 • Redis tracks who is on which server (+ pub/sub routing)
 • Offline = inbox (Redis + DB) + push notification
 • Groups: store ONCE, fan out to online users in parallel
 • Media: pre-signed URLs + CDN, never through chat servers
 • Batch writes (~100× faster)
 • E2EE: Signal protocol; servers can't read
 • Token-bucket rate limits in Redis
 • Shard by user ID + duplicate writes + replicas
 • Plan for Redis + Kafka failures (fallbacks, buffer, disk log)
 • Regions with full stacks; feature flags for safe rollout
```

# 7. Interview Questions & Answers ⭐⭐⭐

> ➕ Short answers you can say out loud. Format: **Q → one-line answer → key words.**

**Q1. How do you start a system design question?**
Clarify functional + non-functional requirements, say what's out of scope, confirm scale, then ask *"does this scope make sense?"*

**Q2. What do interviewers score?**
Communication, structured thinking, technical judgment, practical depth, time management.

**Q3. SQL or NoSQL?**
By requirements. SQL for ACID + joins + consistency (bookings, payments, metadata). NoSQL for huge writes + simple queries (messages). Always say why not the other.

**Q4. Why signed / pre-signed URLs?**
Keep big files off API/chat servers, let clients talk to storage directly, and make links expire.

**Q5. Why a CDN?**
Lower latency, less origin load and egress cost. Use LRU eviction; invalidate when content changes.

**Q6. How do you scale a database?**
1) Read replicas (leader/follower) → 2) shard. **Replication scales reads, sharding scales writes.**

**Q7. Modulo vs consistent hashing?**
Modulo reshuffles almost all data when shard count changes. Consistent hashing (hash ring, next server clockwise) moves only ~1/N. Few stable shards → modulo. Adding often → consistent.

**Q8. User double-clicks "Book". What happens?**
Client-generated reservation UUID + unique key. Duplicate → return the existing reservation (idempotency).

**Q9. Two users book the last room?**
Don't trust read committed alone. Use `SELECT ... FOR UPDATE` (preferred) or serializable (OK at low TPS). Keep a hotel's data on one shard for local transactions.

**Q10. Why Elasticsearch, not SQL, for search?**
`LIKE` = full scan, no ranking, no typo handling, weak geo. ES = inverted index, ranking, fuzzy, geo. Sync with CDC (WAL → Debezium → Kafka → consumer). ES is eventually consistent.

**Q11. Search shows a room that's already booked. Problem?**
No. Search is eventually consistent. The booking path re-checks the DB and invalidates cache keys.

**Q12. Why one inventory row per room type per date?**
Bulk updates, scalable pricing/search, simple overbooking: `reserved + new <= total × factor`.

**Q13. Why WebSockets for chat?**
Persistent two-way channel for instant push. Polling wastes bandwidth and adds delay; long polling churns connections. Cost: Layer-4 LB + memory per connection.

**Q14. How does a message reach an offline user?**
Redis says offline → write to inbox (Redis + DB) → push (APNs/FCM) → on reconnect fetch pending → deliver → read receipt.

**Q15. How do group messages work?**
Group service gives members → check status in Redis → pub/sub to online users' servers in parallel → inbox + push for offline. Store the message once.

**Q16. Multi-device sync?**
Redis tracks all devices → fan out to each → acks/read receipts sync across devices. Last-write-wins + version numbers. Incremental sync (last ~30 days).

**Q17. Why batch DB writes?**
1,000 single inserts ≈ 5 s; one batch ≈ 50 ms → ~100×. Group by conversation. Retry → DLQ on failure.

**Q18. How does E2EE work?**
Identity key pairs (private never leaves device), prekeys on key server, key exchange → session key, ratchet/counter per message. Servers see only ciphertext.

**Q19. How do you rate limit?**
Token bucket per action type in Redis (atomic). Block or CAPTCHA. Progressive penalties up to human review.

**Q20. How do you shard messages?**
By user ID (hotspots), message ID (scatter-gather reads), or timestamp. Good: user ID + duplicate writes + replicas. Ask whether reads or writes matter more.

**Q21. Redis dies. Now what?**
Writes go to Redis *and* DB. Reads try Redis, fall back to DB. Background job re-syncs Redis later.

**Q22. Kafka dies. Now what?**
Replace failed brokers. If the whole cluster is down: bounded local buffer → disk append-only log → replay and republish after recovery.

**Q23. How do you roll out a risky feature?**
Feature flags per environment, gradual % rollout, watch errors, then everyone; strip fields for old clients.

**Q24. Monolith or microservices?**
Monolith = simple transactions, hard to deploy at scale. Full micro = distributed transaction pain. Pragmatic = separate services, shared DB for coupled data.

**Q25. What do you say in the last minutes?**
Summarize decisions, what you sacrificed and why, then extensions for 10× load or more time.

```
 • "Start simple. Add Kafka/sharding only when the numbers justify it."
```

## 8.10 Red Flags

```
 ✘ no clarifying questions      ✘ no numbers
 ✘ no "why" behind tech         ✘ ignoring failures + monitoring
 ✘ SPOF left unaddressed        ✘ cache / search as source of truth
 ✘ silence or monologue         ✘ out of time before scale + trade-offs
```
